# Claude Code コンパクション検証キット

会話が長くなると、Claude Code は古いやり取りを要約に置き換えます（コンパクション）。このキットでは、要約のあとに何が残り、何が消えるのかを、公式ドキュメントの記述どおりか手元で確かめます。

- 参照ドキュメント: https://code.claude.com/docs/en/context-window#what-survives-compaction
- 所要時間: 20分ほど（4つの検証。それぞれ新しいセッションで行います）
- 必要なもの: Claude Code、git、ターミナル（macOS または Linux）
- 少しですがトークンを使います

## 進め方の注意：Claude に任せず、人が手で進める

この検証は、Claude Code に「README どおりに検証して」と頼んでもできません。

- `/compact` やセッションの起動し直しは、人にしかできません。
- 記録する `Read ...` や `Loaded ...` の行は、ターミナルの表示で、Claude 自身には見えません。
- この README には合言葉や予想される結果が書いてあります。Claude が読むと、答えを先に知ってしまい、検証になりません。

clone や `cd` もターミナルで自分で打ち、README は人が読んでください。Claude には、各手順の「 」の文だけを入力します。

## 確かめること

| 検証 | 確かめること |
|---|---|
| 1 | プロジェクト直下の CLAUDE.md は、要約のあとも最新の内容が効いているか |
| 2 | 読んだファイルは要約のあと、更新日時の新しい順に5つまで戻るか。大きいファイルは名前だけになるか |
| 3 | `paths:` 付きのルールは要約で消え、対象ファイルを触ると戻るか |
| 4 | `compact` 用の SessionStart フックは、要約のあとに実行されるか |

## 準備

```bash
git clone https://github.com/cookkawasaki/claude-compact-check
cd claude-compact-check
claude --version
ls ~/.claude/CLAUDE.md
```

- `claude --version` の出力を、結果テンプレート（`result-template.txt`）に書き写してください。
- `ls ~/.claude/CLAUDE.md` でファイル名が表示されたら、個人用の CLAUDE.md があります。自分で作った覚えがなくても存在することがあるので、必ず確かめてください（`No such file or directory` と出れば、ありません）。会社共通の Claude Code 設定があるかも、分かる範囲で書いてください。どちらも結果に影響することがあるためです。
- モデルは Sonnet を勧めます（`/model` で切り替え）。安く、「★ を付ける」のような指示にもきちんと従うためです。エフォート（考える量）の設定があれば、低め〜標準で十分です。
- 初めて `claude` を起動すると、このフォルダを信頼するか聞かれます。許可してください（検証4のフックを動かすため）。

## 共通の約束

- **検証ごとに Claude Code を起動し直してください。** 終わったら `/exit` で閉じ、次の検証は `claude` から始めます。前の検証の内容が混ざらないようにするためです。
- 「 」の中の文は、そのまま入力してください。「Read ツールで」と書いてあるのは、Claude がほかの方法（`cat` コマンドなど）でファイルを見ると、要約のあとに戻るファイルの数に入らず、結果が変わってしまうためです。
- `/compact` を打って「要約するほどの会話がない」という趣旨の表示が出たら、適当にもう1〜2往復話してから打ち直してください。
- 検証の合間に `git status` を打ち、`nothing to commit, working tree clean` と出るか確かめてください。変更されたファイルが出たら、`git restore .` で戻してから次へ進みます。

## 検証1　CLAUDE.md は要約のあとも最新の内容が効いているか

このフォルダの `CLAUDE.md` には「返事の最後の行に ★ を書く」とあります。途中でこれを ◆ に書き換え、要約の前後でどちらが付くかを見ます。

1. `claude` を起動し、「自己紹介を一文でしてください」と入力します。返事の最後に ★ が付くか確かめます。
   - 付かない場合は、個人の設定などが邪魔している可能性があります。テンプレートにそう書き、検証1はここで終えてください。
2. **Claude Code は開いたまま**、別のターミナルを開き、同じフォルダで次を実行します（エディタで ★ を ◆ に書き換えても構いません）。

   ```bash
   perl -pi -e 's/★/◆/g' CLAUDE.md
   ```

3. Claude Code に戻り、「好きな季節を一文で教えてください」と入力します。返事の最後の記号を記録します（要約前）。
4. `/compact` を入力し、要約が終わるのを待ちます。
5. 「好きな果物を一文で教えてください」と入力します。返事の最後の記号を記録します（要約後）。
6. 「ファイルを読まずに答えてください。いまの CLAUDE.md は、返事の最後の行にどの記号を書くよう指示していますか」と入力し、答えを記録します。
7. `/exit` で閉じ、`git restore CLAUDE.md` で元に戻します。

**予想:** 要約後（5）は ◆、6 の答えも ◆。

- 2.1.317 で試したときは、要約前の 3 の時点で既に ◆ になりました。CLAUDE.md の書き換えは、要約を待たずに反映されるようです。3 が ★ だった場合も、そのまま記録してください。
- 要約の文章の中に「★ を付ける」という指示が書き残されることがあります。5 で ★ が出ても、6 で ◆ と答えれば、最新の CLAUDE.md が効いています。

## 検証2　読んだファイルは更新日時の新しい順に5つまで戻るか

`files/` には、小さいファイル6つ（`small1.txt`〜`small6.txt`）と、大きいファイル1つ（`big.txt`、約1万トークン）があります。

ドキュメントには「更新日時（ファイルが最後に変更された日時）の新しいものから5つ」とあります。そこで、**読ませる順番と、更新日時の順番をわざと逆にします。** どちらの順で選ばれたかが、結果から分かります。

1. `claude` を起動する**前に**、次のコマンドでファイルの更新日時をそろえます（small1 がいちばん新しく、small6 がいちばん古くなります）。

   ```bash
   touch -t 202601010106 files/small1.txt
   touch -t 202601010105 files/small2.txt
   touch -t 202601010104 files/small3.txt
   touch -t 202601010103 files/small4.txt
   touch -t 202601010102 files/big.txt
   touch -t 202601010101 files/small5.txt
   touch -t 202601010100 files/small6.txt
   ```

2. `claude` を起動し、「Read ツールで files/small1.txt と files/small2.txt を読んで、それぞれの合言葉を答えてください」
3. 「Read ツールで files/small3.txt から files/small6.txt までの4つを読んで、それぞれの合言葉を答えてください」
4. 「Read ツールで files/big.txt を最初から最後まで読んで、最初の行と最後の行を答えてください」
5. `/compact` を入力し、要約が終わるのを待ちます。
6. **要約の直後に出る行を、そのままテンプレートに貼り付けます。** `Compacted` の行の下に、次のような行が並びます。

   ```
   ⎿  Compacted (ctrl+o to see full summary)
      Read files/small1.txt (2 lines)
      Read files/small2.txt (2 lines)
      （…ほかの Read 行が続く…）
      Referenced file files/big.txt
   ```

   - `Read ...`：中身ごと読み直されたファイル
   - `Referenced file ...`：大きすぎて、名前だけが戻ったファイル
   - こうした行が1行も出なかった場合は、「表示なし」と書いてください。
7. 参考として、「ファイルを読まずに答えてください。いま中身が分かるファイルと、名前しか分からないファイルを挙げてください」と入力し、答えを貼り付けます。
8. `/exit` で閉じます。

**予想（ドキュメントどおりなら）:** `Read` は small1〜small4 の4つ、`Referenced file` は `files/big.txt`。small5 と small6 は出てこない。

- 「5つまで」のうち1枠は big.txt が使うので、`Read` が4つなのは予想どおりです。

- もし `Read` が small3〜small6 になったら、更新日時ではなく「読んだ順」で選ばれています。
- small5・small6 の合言葉を 7 で答えられても、問題ありません。ファイルとしては戻らなくても、要約の文章に書き残されることがあります。
- Claude が `head` や `tail` などのコマンドで big.txt を見た場合は、Read ツールで読んだことにならず、結果が変わります。手順2〜4以外のファイル（README など）を Claude が自分から読んだ場合も、それが数に入ります。どちらもテンプレートに書いてください。

## 検証3　`paths:` 付きのルールは要約で消え、また戻るか

`.claude/rules/api.md` には、`api/` のファイルを触るときだけ読み込まれるルール「返事の最初に【API】と書く」があります。ルールが読み込まれると、ターミナルに `Loaded .claude/rules/api.md` という行が出ます。

要約のあとに戻る5つのファイルには、ルールのファイル自体も入ります。そのままだとルールがファイルとして戻ってしまうので、**ルールのファイルを古い日付にし、新しいファイルを後から5つ以上読ませて**、戻る5つから外します。

1. `claude` を起動する**前に**、次のコマンドを実行します。

   ```bash
   touch -t 202501010000 api/sample.ts .claude/rules/api.md
   ```

2. `claude` を起動し、「api/sample.ts を読んで、何をする関数か一文で教えてください」と入力します。`Loaded .claude/rules/api.md` の行が出たかと、返事の最初に【API】があるかを記録します。
3. 「Read ツールで files/small1.txt から files/small6.txt までの6つを読んで、それぞれの合言葉を答えてください」と入力します。
4. `/compact` を入力し、要約が終わるのを待ちます。要約の直後に出る行（`Read ...` など）を、そのまま貼り付けます。
5. 「ファイルを読まずに答えてください。さっきの関数の名前は何でしたか」と入力します。【API】があるか記録します。
6. 「Read ツールで api/sample.ts をもう一度読んで、引数の数を答えてください」と入力します。`Loaded .claude/rules/api.md` の行が出たかと、【API】があるかを記録します。
   - Claude がファイルを読まずに答えた場合（`Read 1 file` などの表示が出ない場合）は、「Read ツールで読み直してください」と言い直してください。
7. `/exit` で閉じます。

**予想:** 2 は Loaded あり・【API】あり。4 の直後は `Read files/small1.txt` 〜 `Read files/small5.txt` の5行で、`api/sample.ts` と `.claude/rules/api.md` は出てこない。5 は【API】なし。6 は Loaded あり・【API】あり。

- 4 の直後に `.claude/rules/api.md` が出た場合は、ルールのファイルが戻っています。1 の `touch` を実行したか確かめてください。
- 5 で【API】が付いた場合は、要約の文章にルールが書き残された可能性があります。`ctrl+o` で要約の全文を開き、【API】のルールが書かれているか見て、記録してください。

## 検証4　`compact` 用の SessionStart フックは、要約のあとに動くか

`.claude/settings.json` に、要約の直後だけ「検証用の合言葉は いちょう です。」と Claude に伝えるフックがあります。

1. `claude` を起動します。
2. 「ファイルを読まずに答えてください。検証用の合言葉を知っていますか。知らなければ『知らない』と答えてください」と入力し、答えを記録します。
3. `/compact` を入力し、要約が終わるのを待ちます。
4. 2と同じ文を入力し、答えを記録します。
5. `/exit` で閉じます。

**予想:** 2 は「知らない」、4 は「いちょう」。

- 合言葉はこの README と `.claude/settings.json` にも書いてあります。Claude がどこかのファイルを読んでから答えた場合は、テンプレートに書いてください。
- 検証をやり直すときは、`/memory` で auto memory に合言葉が保存されていないか確かめてください。保存されていると、要約前から「いちょう」と答えてしまいます。
- 会社の設定でプロジェクトのフックが禁止されていると、4 も「知らない」になります。その場合は「フック禁止かも」と書いてください。

## 結果のまとめ方

1. `result-template.txt` の中身を、メモアプリやエディタにコピーします（リポジトリの中には保存しないでください。`git status` が汚れます）。
2. 各項目の `:` のあとに答えを書きます。`（ ）` の中は書き方の案内なので、消して構いません。
3. 「そのまま貼る」とある欄には、ターミナルの表示をそのまま貼り付けます。
4. 予想と違った点は、最後の「気づいたこと」に書きます。
5. 誰かに見せる前に、**社内のフォルダ名やプロジェクト名、ユーザー名、PC 名が混ざっていないか**確認してください。

すべて終わったら、次のコマンドで元の状態に戻せます（`touch` で変えた更新日時は戻りませんが、検証には影響しません）。

```bash
git restore .
git status   # 「nothing to commit, working tree clean」と出れば元どおり
```
